# Where the agent got it wrong

One row every time Claude (or any agent, or the build guide itself) gets something wrong and I
catch it. This is the source of new rules in `CLAUDE.md` / `AGENTS.md`, and it is the honest
answer to "tell me about a time an agent got something wrong."

The format is deliberate: **what it did → why it looked right → how I caught it → the rule or
test that stops a repeat.** A story without the last column is a complaint, not an engineering
practice.

| Date | Task | What it did | How I caught it | What I changed (fix + rule/test added) |
|------|------|-------------|-----------------|----------------------------------------|
| 2026-09-22 | Project setup | The build guide's `vitest.config.ts` calls `config({ path: '.env.test' })`, which also *mutates* `process.env` in the config file as a side effect. Looks harmless. | Read the installed dotenv v18 type definitions before copying the snippet. v18 added `processEnv` and a `quiet` flag; v16 (what the guide was written against) had neither. | `config({ path, quiet: true, processEnv: {} })` — parse into a throwaway object and hand it to Vitest via `test.env`, so the config file cannot leak the test DB URL into the dev process. |
| 2026-09-22 | Project setup | Installed `vitest@5` alongside `@types/node@20`; pnpm printed an unmet-peer warning rather than failing. | Read the install output instead of scrolling past it. | Bumped to `@types/node@^22` (Node 22 LTS is what we run). Lesson: a peer warning is a type-level time bomb, not noise. |
| 2026-09-22 | First `pnpm db:migrate` | `drizzle-kit migrate` failed with a spinner and bare `exit code 1` — **no error message at all**. Easy to misread as "the SQL is wrong". | Applied each `drizzle/*.sql` by hand to a throwaway `clinicdesk_probe` database with `psql -v ON_ERROR_STOP=1`: all four applied cleanly. So the SQL was fine and the tool was hiding something. Ran the same migration through drizzle-orm's `migrate()` (which `tests/global-setup.ts` uses) and got the real error: `28P01 password authentication failed for user "clinic"`. | Root cause: a natively installed **PostgreSQL 17 Windows service** owns host port 5432, so `localhost:5432` never reached the Docker container. Published a second port `5433:5432` and taught `vitest.config.ts` + `tests/global-setup.ts` to prefer a shell `DATABASE_URL` over `.env.test`. Rule learned: when a tool swallows an error, reproduce the same operation through a layer that doesn't. |
| 2026-09-23 | tRPC error mapping | The `mapDomainErrors` middleware mapped `DomainError` correctly and let everything else "fall through to a generic 500" — which its own comment, and my guide chapter, both claimed. Neither was true: tRPC builds a message as `opts.message ?? cause?.message ?? opts.code` and `getErrorShape` serialises it unconditionally (only `stack` is dev-gated). So `throw new Error("Insert returned no row")` in a service, a rethrown Stripe error, or a driver's `connect ECONNREFUSED <host>:<port>` went **verbatim to the browser**. | A read-only security-review agent traced it into `@trpc/server`'s own source rather than trusting the comment. I verified it myself at `tracked-D4jU_Hb3.mjs:39`, then proved it by test. | Middleware now replaces the message on any `INTERNAL_SERVER_ERROR` with a fixed string, keeping the real error as `cause` so `onError` still logs it — and leaves Zod `BAD_REQUEST`s alone so forms keep their field errors. Added two regression tests, then commented out the fix to watch the leak reappear as `'Insert returned no row: secret internal detail'`. **Lesson: a comment asserting a framework's behaviour is a hypothesis until you read the framework.** |
| 2026-09-23 | Running several build agents in parallel | Two agents ran `pnpm test` at the same time against the one shared `clinicdesk_test` database. Symptoms were bizarre and looked like application bugs: a `services` row vanishing between its own INSERT and a later query **in the same test**, FK violations against an id that had just been inserted, `mcp.test.ts` reporting "Expected at least one service". | An agent reported the symptom honestly instead of "fixing" its test to match. The giveaway was a row disappearing mid-test — no application bug can do that; only another connection's `TRUNCATE` can. | `fileParallelism: false` only serialises files **within one Vitest process**; it cannot stop a second process. Protocol changed: **only the lead runs the suite**, agents run `typecheck`/`lint` only. The real fix for parallel work is a database per worktree (`clinicdesk_test_<branch>`), which `vitest.config.ts` and `tests/global-setup.ts` already support via a shell `DATABASE_URL` override. |
| 2026-09-22 | Annotating migration `0003` | I added an explanatory comment to a generated migration that happened to contain the literal marker Drizzle writes between statements. The migrator split the file **inside my comment** and sent the fragment `` ` handling — which is exactly why you…`` to Postgres → `42601 syntax error at or near "` ``"`. | The test run failed with the query text printed, and the query was obviously half a comment. | Reworded the comment so the marker never appears in prose. Rule: generated migration files have in-band signalling; prose in them is not inert. (This one was mine, not an agent's — same discipline applies.) |
